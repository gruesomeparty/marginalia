# The landing page

One static page, no build step, no external requests — the same rules the
product's own page follows.

`demo.html` is **not** committed. It is a real `marginalia export` of
`demo/handover.md`, generated by `scripts/demo.sh` — which
`.github/workflows/pages.yml` runs at deploy time from the binary in that
commit, so the demo in the hero can never drift from the product it
demonstrates.

To preview locally:

```bash
scripts/demo.sh                 # writes site/demo.html
python3 -m http.server -d site 8080
```

`demo/feedback.jsonl` is the seeded review: a sentence-level question, the
agent's threaded answer, a blocker on a diagram edge, and one approval. It is
committed so the demo always shows a review in progress rather than an empty
page.

The diagram is **drawn**, not shown as source: the argument the hero is making
is that the shape you click is the statement your note lands on, and that only
lands if there is a picture to click. Drawing needs mermaid's own CLI, so the
workflow installs it and the deploy fails rather than publishing a hero with
the feature quietly missing. Without `mmdc` on your machine,
`scripts/demo.sh site/demo.html off` previews everything else against the
anchored source:

```bash
npm i -g @mermaid-js/mermaid-cli   # and, as root, the puppeteer args the
                                   # README's diagram section spells out
```

The script also enforces the product's own rule on the way out — an exported
review loads nothing — and fails if the page ever gains an external reference.
XML namespace URIs are the one allowed match: a drawn SVG always carries them,
and they are identifiers, never requests.
